# StratHive（策略蜂巢）—— 产品定位与核心架构设计

## 1. 产品定位

### 1.1 产品愿景

StratHive 是面向个人投资者的 AI Native 投资管理系统，帮助用户从主观、零散的交易行为走向有计划、有纪律、可追踪、可评价、可持续改进的体系化投资。

借鉴现代投资机构的 PMS（投资组合管理系统）与 OMS（订单管理系统），将其简化并改造为适合个人投资者使用的形态。

**核心价值：不限定投资者如何产生投资决策，而是将任意形式的投资策略纳入统一的投资管理闭环。**

### 1.2 目标用户

- 已经习惯使用 AI 助手的个人投资者。
- 优先面向 A 股股票、ETF 投资者。
- 不要求具备编程、量化交易或专业投资研究能力。
- 希望逐步建立自己的投资体系，改善交易行为，提高投资管理效率。

### 1.3 产品原则

- **AI Native**：充分利用用户已有的个人 Agent，通过 CLI、Skills 等方式提供专业投资管理能力，不重复建设 Agent Harness。
- **策略中心化**：以策略及其独立的投资实践为核心，而不是以券商账户或交易程序为核心。
- **人工交易是一等公民**：充分考虑 A 股普通投资者难以获取券商 API 的现实，不依赖账户查询及自动交易接口即可形成完整业务闭环。
- **开放性**：兼容主观交易、人工规则、LLM 辅助决策、程序化交易以及各种混合形式。
- **渐进式成长**：用户可以从自然语言记账开始，逐步引入交易纪律、策略监督、AI 辅助决策和自动化。
- **实用优先**：以真实使用需求驱动功能演进，不追求大而全的金融基础设施。

### 1.4 差异化价值

StratHive 不是传统交易日志工具、量化交易框架或 AI 投资研究平台。

其核心差异在于：允许用户将任意形式的投资策略作为相对独立的虚拟投资组合进行管理，即使多个策略共享同一个真实券商账户，也能够独立管理其资金、持仓、交易决策、执行情况及投资绩效。

产品追求的不是更强的投资决策能力，而是更好的投资过程管理能力。

## 2. 策略建模与管理

### 2.1 核心领域模型

统一策略的业务语义，而不是统一策略的表达形式和执行方式。

核心领域对象：

- **Strategy（策略）**：一种投资思想、方法或规则的定义。
- **Asset Account（资产账户）**：对应一个真实券商账户的记账对象，记录账户现金和持仓。
- **Strategy Run（策略运行）**：在一个资产账户内，基于某个策略开展的一段投资实践，是资产归属与绩效核算的单位。
- **Trade Instruction（交易指令）**：投资决策方交付执行的交易要求，描述交易目标与执行范围。
- **Trade Log（交易日志）**：归属于策略运行的交易操作及实际成交记录，其中的成交记录用于更新资金和持仓。

一个策略可以有多个策略运行。一个资产账户也可以容纳多个策略运行，各自管理资金、持仓、交易记录和投资绩效。账户现金由各运行现金和未分配现金组成，账户持仓按数量归属到各运行。

策略运行启动时分配期初资产，结束时归还剩余现金，持仓可通过实际卖出结清或在同一资产账户内交接给新运行。对账核对券商数据与资产账户账本，并检查账户总量与各运行的资产归属是否一致。

Strategy Run 表示投资业务生命周期，不等同于程序运行实例、Agent 会话或单次策略计算任务。

### 2.2 策略表达

策略的概念应尽可能宽广，包括但不限于：

- 完全依靠个人主观判断的交易。
- 基于自然语言规则的人工交易。
- 基于 Prompt 或 Skills 的 LLM 辅助交易。
- 基于明确数学规则的程序化交易。
- 上述方式的任意组合。

Strategy 可以包含基本元信息、描述文档、参数配置及外部实现引用。具体策略可以使用 Markdown、JSON、Prompt、代码仓库等不同形式表达。

StratHive 不要求策略必须具备明确规则、可执行代码或固定的实现形式。

### 2.3 基于属性与能力的策略建模

不采用基于固定策略类型的继承体系，不将人工策略、LLM 策略、量化策略设计成互斥的领域实体。

借鉴从 RBAC 到 ABAC 的抽象思路，采用基于属性和能力的建模方式（Capability-based Modeling）。

策略可以具备若干相互独立的属性和能力：

| 维度 | 示例 |
|---|---|
| 表达形式 | 无明确规则、自然语言、Prompt、代码 |
| 决策主体 | 人工、LLM、确定性程序或混合 |
| 执行方式 | 人工、按需触发、定时执行、持续运行 |
| 版本化能力 | 是否具备可追溯的策略版本 |
| 回测能力 | 是否能够基于历史数据进行有效回测 |
| 交易指令能力 | 是否能够主动生成交易指令 |
| 监督能力 | 是否能够上报执行结果或心跳 |
| 交易执行方式 | 人工执行、程序化执行 |

上述维度彼此独立，不要求一个策略只能选择某种固定组合。

例如，一个策略可以由确定性程序筛选标的，LLM 分析市场情况，最终由用户做出投资决策并手动完成交易。

不同形式的策略可以具有不同的能力：

| 能力 | 主观交易 | 人工规则 | LLM 策略 | 程序化策略 |
|---|---|---|---|---|
| 明确规则描述 | 可选 | 通常具备 | 通常具备 | 通常具备 |
| 版本管理 | 可选 | 可选 | 可支持 | 可支持 |
| 自动回测 | 通常不支持 | 视规则而定 | 较困难 | 视实现而定 |
| 自动执行分析 | 不适用 | 可选 | 可支持 | 可支持 |
| 交易指令记录 | 可选 | 可选 | 推荐 | 推荐 |
| 资金与持仓管理 | 支持 | 支持 | 支持 | 支持 |
| 绩效分析 | 支持 | 支持 | 支持 | 支持 |

此表仅用于说明能力差异，并非固定的策略分类规范。

产品根据策略实际具备的能力提供相应功能，而不是根据策略类型强制启用或禁用功能。

**现阶段不建设通用能力注册框架，也不提前实现所有属性。** 随着实际业务需求增加必要的属性、配置及关联资源即可。

### 2.4 策略版本管理

版本管理是策略的可选能力。

- 纯主观策略：投资思想可能持续发生微妙变化，无需强制版本化。
- 人工规则策略：可以对明确的规则文档进行版本化。
- LLM 策略：可以记录 Prompt、Skill、模型配置及相关规则的版本。
- 程序化策略：可以记录代码版本、参数配置及相关实现引用。

对于启用版本管理的策略，应保证已使用的历史版本可追溯，避免修改当前策略定义后丢失历史决策依据。

版本可以通过文档快照、Git Commit、配置快照等方式管理，StratHive 不必自行存储和管理所有策略实现资源。

启用版本管理的策略在创建运行时绑定一个版本，整个运行期间沿用该版本。同一版本可用于多个运行。采用新版本开展投资时创建新运行，需要延续的持仓可通过同账户交接承接。这样每个运行都有明确的策略依据，可以独立评价绩效。未启用版本管理的策略可直接创建运行。

现有 MVP 为每个策略维护版本快照，并在创建运行时绑定版本。版本可选是后续策略建模的方向。

需要注意，版本可追溯不等于策略决策必然可复现，特别是 LLM 策略还受到模型、输入数据及执行环境等因素影响。

### 2.5 策略运行架构

StratHive 负责投资业务管理，不负责策略程序的实际运行。

各类策略可以运行在任意环境中，包括人工、个人 Agent、独立脚本及成熟量化框架。

策略通过 CLI、Skills、SDK 或未来的 API 使用 StratHive 提供的业务能力，包括：

- 查询策略定义、资金、持仓及历史交易。
- 提交交易指令。
- 记录实际成交。
- 查询策略运行状态及投资绩效。

现阶段不建设统一 Strategy Executor SPI、Strategy Runtime、通用任务调度、进程管理及 Agent Harness。

执行环境自行负责策略计算、定时任务和程序生命周期。

### 2.6 策略运行生命周期

StratHive Core 统一管理 Strategy Run 的业务状态：

| 状态 | 含义 |
|---|---|
| ACTIVE | 正常开展投资活动 |
| PAUSED | 暂停提交新交易指令及主动投资活动 |
| CLOSED | 投资活动结束，保留历史记录 |

Core 必须强制执行状态约束：

- 暂停或结束后，不允许提交新交易指令。
- 暂停不影响已有持仓的估值、对账及绩效计算。
- 结束前必须处理剩余资金和持仓的归属。
- CLOSED 为终态，继续开展投资活动应创建新的 Strategy Run。
- 允许符合有效运行期间及账本一致性要求的历史成交补录和修正。
- 结束后发生的新成交不得归入已结束的运行实例。

Core 无法控制外部策略是否继续运行，但能够控制其业务操作是否合法，并且不得因状态限制而丢弃真实发生的交易事实。

### 2.7 交易管理

借鉴投资机构投资决策与交易执行分离的思想，提供轻量级个人 OMS 能力。

标准业务路径：

策略决策 → 交易指令 → 审核与执行 → 交易日志 → 账本更新 → 绩效评价与复盘。

交易指令可以给出明确的价量，也可以描述目标成本区间、数量范围等要求，由执行者在授权范围内选择成交时机和方式。

其中：

- 交易指令可以被接受、拒绝、修改、取消或过期。
- 一个交易指令可以关联多笔实际成交。
- 人工交易允许直接记录实际成交，不强制补建交易指令。
- 交易指令本身不改变真实资金和持仓。
- 只有实际成交及其他有效账本事件才能改变资产账本。

不复制机构投资管理中的复杂岗位分工和审批流程。

### 2.8 策略运行监督

StratHive 不负责运行策略，但负责发现投资活动中可能出现的问题。

建设轻量级监督能力，关注：

- 策略活跃度及预期执行情况。
- 策略执行异常、超时或状态未知。
- 账本对账时间及一致性。
- 未处理或已过期的交易指令。
- 异常资金、持仓及投资风险。

区分三类独立状态：

- 投资业务状态。
- 策略执行健康状态。
- 账本可信状态。

没有交易不等于没有活动。自动化策略可以上报本次执行结果或心跳，人工策略通过定期确认和对账维持账本可信度。

根据策略实际具备的能力及预期活动频率选择监督方式，不强制所有策略上报心跳。

监督结果优先通过投资日报等方式统一呈现，紧急问题可以即时通知。

日报触发、定时调度及消息投递可委托个人 Agent，不必在 StratHive 中建设完整调度系统。

## 3. 数据服务设计

### 3.1 模块定位

市场数据服务与 StratHive Core 在逻辑上相互独立。

Core 负责投资事实及业务规则，数据服务负责提供行情、证券基础信息及其他投资相关数据。

数据服务可以被 Core、个人 Agent、外部策略及量化框架使用，但不是所有策略获取市场数据的强制入口。

外部策略可以自行选择适合自己的数据源。

### 3.2 技术路线

优先复用现有开源金融数据基础设施，避免从零建设完整的数据采集、清洗、存储和查询平台。

当前优先试用：

- CNEquity：https://github.com/rootSunc/CNEquity

重点验证其 A 股及 ETF 数据覆盖、历史行情、本地存储、增量更新和查询能力。

CNEquity 主要作为历史数据基础设施候选，其盘中行情能力、数据质量、稳定性及数据授权需要实际验证，不预设其能够满足全部实时行情需求。

对于无法满足的需求，再按需引入其他数据源或实现轻量适配层。

### 3.3 数据服务建设原则

- 不要求所有数据预先同步至本地。
- 不强制采用统一存储引擎。
- 不提前建设全市场实时行情采集系统。
- 优先复用成熟的数据源、存储及分析组件。
- 按需处理数据缓存、来源标记、时效性、质量检查及主备切换。

参考存储方式：

| 数据类型 | 建议方案 |
|---|---|
| 最新行情 | 内存或轻量本地缓存 |
| 历史行情 | 复用 CNEquity 等本地数据基础设施 |
| 大规模历史分析数据 | Parquet + DuckDB 等 |
| 投资业务账本 | 独立 SQLite 数据库 |

### 3.4 量化框架兼容

不要求 StratHive 数据服务直接兼容所有量化框架的数据接口。

优先保证金融数据基本语义明确，包括证券标识、交易所、交易时间、价格、成交量、复权方式及数据来源等。

在实际接入 Backtrader、RQAlpha、vn.py 等框架时，再根据其数据接口开发对应适配器。

不为尚未确定的量化框架兼容需求提前设计通用抽象。

### 3.5 建设优先级

- **P0：账本估值**——最新价格、证券基础信息等。
- **P1：策略辅助**——实时行情、历史 K 线等。
- **P2：研究与回测**——财务数据、复权、历史成分股、时点数据等。

按照实际投资使用需求逐步建设。

## 4. 整体系统边界

| 模块 | 核心职责 |
|---|---|
| StratHive Core | 策略管理、资金分配、交易管理、投资账本、运行监督、绩效与复盘 |
| StratHive Data | 市场数据获取、查询及必要的数据适配 |
| 外部策略 | 投资研究、分析与决策 |
| 个人 Agent | 用户交互、策略辅助执行、调度及消息投递 |
| 券商 | 实际交易执行及成交事实确认 |

其中：

- StratHive 是投资业务中心。
- 各类策略是投资决策主体。
- 个人 Agent 是统一的自然语言交互入口。
- 券商是实际交易事实的最终外部依据。

StratHive Core 应成为用户投资管理数据的唯一权威来源，但不垄断市场数据、投资决策和用户交互。

## 5. 当前阶段与演进原则

当前 MVP 已实现：

- 核心策略运行账本，覆盖资产账户、策略与运行管理、资金与持仓归属、交易日志、持仓交接和对账。
- CLI 和 Agent Skills。

暂不建设 Web UI、完整行情服务、投资分析、策略运行时等能力。

MVP 之后，两条主线并行推进。

1. **接入数据服务**。试用 CNEquity 等开源方案，验证其能否满足证券基础信息、账本估值和历史行情的需要，再根据验证结果确定接入方式。
2. **完善策略建模与策略运行管理**。在现有账本之上逐步支持不同策略表达和可选的版本管理，补充交易指令、运行监督和复盘能力，让运行表现和执行结果可用于调整策略。

核心账本的正确性、资金与持仓归属、业务状态约束和数据可靠性必须严格保障；外围模块允许采用简单、实用、可替换的实现。

**不追求架构上的完美和功能上的大而全，不为尚未发生的需求支付过高的开发与维护成本。**

StratHive 最终应拥有的是：

**策略定义 → 投资实践 → 决策记录 → 交易执行 → 绩效评价 → 策略改进**

这一完整投资业务闭环，而不是底层所有技术基础设施的所有权。
